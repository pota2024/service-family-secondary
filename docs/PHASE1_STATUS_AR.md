# حالة المرحلة 1

## ما تم تنفيذه فعليًا
- **الهوية:** أزرق ملكي/سماوي/ذهبي، RTL، خط Cairo، وضع داكن اختياري، بطاقات وأزرار وشريط تنقل على نسق المرجع.
- **المقدمة:** سماء متحركة وسحب وحركة ركض وظهور الاسم، تخطي بعد ثانيتين، مكان واضح للصورة الأصلية.
- **الدخول:** رقم هاتف + كلمة مرور بدون SMS (Firebase Email/Password ببريد داخلي مشتق مجزّأ SHA-256 من الرقم المطبّع E.164). منع التكرار، تطبيع الأرقام العربية/المحلية/الدولية، رسائل خطأ عربية، تغيير كلمة المرور من الملف الشخصي.
- **التسجيل:** 5 خيارات (عام مخفي حتى كود 0001)، صورة شخصية مضغوطة ≤180KB داخل `profiles.photoUrl` كـ data URI، تاريخ ميلاد للمخدومين، كود 2580 للخدام (واجهة فقط).
- **الموافقة:** تبويب «الطلبات»: خادم البنين/البنات يقبل ويرفض مخدومي قسمه فقط؛ العام يقبل كل شيء بما فيه ترقية خادم/عام. يُسجَّل المراجع والوقت ويُنشأ إشعار للمستخدم.
- **الحالات:** pending / active / rejected / suspended (لا دخول للوظائف إلا active). وضع الصيانة وتعطيل قسم من `settings/app`.
- **الرئيسية والملف:** بيانات حقيقية من Firestore؛ مجموع النقاط يُحسب لحظيًا من سجل `points`.
- **قواعد Firestore لكل المجموعات** (users, registrationRequests, profiles, privateUsers, attendance, points, activities, competitions, competitionSubmissions, chats+messages, notifications, settings) + ~90 اختبارًا.
- **GitHub Actions:** بناء APK، تحليل، اختبارات وحدة، واختبار القواعد.

## قرارات أمنية
| البند | القرار |
|---|---|
| ترقية النفس | مستحيلة: التسجيل يفرض `role=member`+`pending`، والدور المطلوب يُحفظ في `registrationRequests` فقط. تعديل `users` للعام، أو للخادم (الحالة فقط، لمخدومي قسمه، وليس طلبات الخدام). |
| الكودان | واجهة فقط. أي شخص قد يستخرجهما من التطبيق. |
| أول عام | يدويًا من Firebase Console (انظر SETUP). |
| نقاط المسابقة | معرّف النقطة `comp_{competition}_{uid}` + شرط أن المشاركة approved ⇒ لا تكرار. |
| الحضور | معرّف `eventId_uid` ⇒ لا تكرار؛ لا تعديل، الحذف لمدير القسم. |
| النقاط | سجل إضافة فقط؛ التصحيح للعام. |
| الشات | غرف ثابتة بقواعد حسب الدور والقسم. |
| خصوصية | الهاتف وتاريخ الميلاد في `privateUsers` (المالك والعام فقط). الخادم **لا** يرى الهواتف. |

## ما يحتاج إعدادًا يدويًا منك
1. تفعيل Email/Password، إنشاء Firestore، نشر القواعد، إنشاء أول حساب عام (SETUP_AR).
2. صورة المقدمة الأصلية.
3. تقييد مفتاح API وتوقيع ثابت (اختياري الآن).

## قيود معروفة (بصراحة)
1. **نسيان كلمة المرور:** غير ممكن آليًا مجانًا. لا يوجد بريد حقيقي أو SMS، وتغيير كلمة مرور مستخدم آخر يحتاج Firebase Admin عبر Cloud Functions (Blaze). المتاح: تغيير كلمتك وأنت داخل التطبيق، وإعادة إنشاء الحساب بعد حذفه من Console (يفقد المستخدم ارتباطه بسجل النقاط القديم). **قرار مطلوب منك** لاحقًا: القبول بهذا أو اعتماد بديل.
2. **ملكية الرقم غير مُثبتة:** أي شخص يستطيع التسجيل برقم غيره. الاعتماد الإداري هو خط الدفاع.
3. **لم أستطع تشغيل Flutter أو المحاكي هنا** (بيئتي بلا إنترنت). الكود كُتب ودُقق يدويًا لكن لم يُترجَم ولم تُجرَّب القواعد فعليًا. أول بناء على GitHub قد يُظهر أخطاء ترجمة صغيرة سأصلحها فور وصول السجل. نجاح البناء لا يعني صحة كل الوظائف؛ جرّب سيناريوهات التسجيل والاعتماد.
4. استعلامات المخدوم على الأنشطة والمسابقات بـ `in ['boys','all']` قد تحتاج استعلامين منفصلين بسبب طريقة تقييم القواعد؛ أتحقق منها بالاختبارات في المرحلة 3.
5. توقيع APK مؤقت حتى تضيف أسرار التوقيع.

## الانحرافات الموثقة عن هيكل Firestore المطلوب
- `registrationRequests` لها حقول: uid, displayName, requestedRole, requestedSection, status, createdAt, reviewedBy, reviewedAt.
- `profiles.photoUrl` يحمل data URI مضغوطًا (بدل رابط Storage).
- `notifications.uid` يقبل أيضًا `boys` / `girls` / `all` للإعلانات الجماعية.
- الحضور والنقاط والمشاركات بمعرّفات حتمية لمنع التكرار.
- أضفت 5 معرّفات ثابتة للشات: boys_members, girls_members, boys_servants, girls_servants, servants_all.
